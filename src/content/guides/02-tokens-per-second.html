An interactive field guide

Tokens per second, from one byte to the frontier

A language model answers one small piece of text at a time. How fast those pieces arrive is set by a short list of physical facts: how many bytes the chip must move per piece, how fast it can move them, how many people share the chip, and a handful of tricks that bend those limits. This page builds the number from scratch and then shows every trick.

This is what a speed feels like. A fast reader manages about 6 tokens a second, so anything above that is faster than you can read. Code, tool calls and "thinking" are consumed by machines, and for those the ceiling is as high as physics allows.

00 · PLAIN WORDS

Every term, in one breath

The chapters use these words freely. Each entry is a one-sentence definition and a picture to hold it by. Dotted-underlined terms in the chapters link back here. Nothing on this page assumes you know any of them already.

Token
The unit a model reads and writes: a word, a piece of a word, a number, a punctuation mark. In English one word is about 1.3 tokens; code and other languages run higher.A tile. Everything on this page is about how fast tiles come out of the machine.
Tokens per second tok/s · TPS
How many tokens arrive each second once the answer has started. The headline speed number. It is almost always quoted for the output, not the prompt, and for one user, not the whole server.The speedometer. Not the whole story, because the car also has to start.
Time to first token TTFT
The pause between sending a request and the first token coming back. Set mostly by how long the prompt is, because the model must read all of it before it can write anything.How long the engine cranks before it catches.
Time per output token TPOT · ITL
The gap between one output token and the next, usually in milliseconds. Tokens per second is just 1000 divided by this. Also called inter-token latency.The tick of the metronome. 20 ms per tick is 50 tok/s.
Latency vs throughput
Latency is how long one person waits. Throughput is how much work the whole system finishes per second. They pull against each other: serving more people at once makes each one slightly slower.A bus is high throughput; a taxi is low latency. Same road.
Prefill
The first phase of a request: the model reads the whole prompt in one pass and builds its working memory of it. All prompt tokens are processed at once, so this phase is heavy on arithmetic.Reading the brief before writing a word.
Decode
The second phase: the model produces output one token at a time, each one requiring a full pass through the model. This is where tokens per second lives.Typing the reply, one key at a time, re-reading your notes before every key.
Forward pass
One trip through all the model's layers to produce one prediction. Decode is one forward pass per output token. Prefill is one forward pass over the whole prompt at once.One turn of the crank.
Parameters, weights P
The learned numbers that make up the model. A "70B model" has seventy billion of them. They are fixed, and every single one is read from memory on every forward pass.The model's long-term memory. Reading it in full, every tick, is the whole speed problem.
Precision, bytes per parameter bf16 · fp8 · int4
How many bytes each parameter takes in memory. bf16 is 2 bytes, fp8 is 1, int4 is half a byte. Fewer bytes means fewer bytes to move per token, so faster decode.Writing the same number in big handwriting or small handwriting.
Quantization
Converting a trained model's parameters to a lower precision after training. The model gets smaller and faster; done carelessly it gets slightly dumber.Compressing a photo. Mostly invisible until you push it too far.
FLOPs
Floating-point operations: the count of multiplications and additions. Each token costs about 2 × P FLOPs (one multiply and one add per parameter). Chips are rated in FLOPs per second.The arithmetic bill. Surprisingly, it is usually not the thing that limits speed.
Memory bandwidth, HBM
How many bytes per second the chip can pull from its main memory. HBM (high-bandwidth memory) is the fast memory stacked next to a GPU: an H100 reads 3.35 terabytes per second from it.The width of the pipe between the pantry and the kitchen.
Memory-bound vs compute-bound
A memory-bound step spends its time waiting for bytes to arrive. A compute-bound step spends it doing arithmetic. Decode is memory-bound; prefill is compute-bound. Everything else on this page follows from that one sentence.A chef who is either walking to the pantry or chopping. You can only speed up the one they are doing.
Arithmetic intensity
FLOPs performed per byte moved. If it is low, the chip starves for data; if it is high, the chip is busy. Each chip has a crossover point, and a decode step for one user sits far below it.How much chopping you do per trip to the pantry.
Roofline
The chart that puts arithmetic intensity on the x axis and achievable speed on the y axis. Left of the crossover the roof slopes up (bandwidth limits you); right of it the roof is flat (compute limits you).The shape of the ceiling you are standing under.
Batch size B
How many requests the chip handles in one forward pass. Reading the weights once and using them for 64 users costs about the same as using them for 1, so batching is how servers get throughput almost for free.Taking the pantry trip once and cooking for the whole table.
Continuous batching
Letting requests join and leave the batch at every token step instead of waiting for the whole batch to finish. The standard since 2023; without it a server idles while one long answer finishes.A bus that picks up and drops off at every stop rather than only at the depot.
KV cache
The model's working memory of everything in the conversation so far: for each past token, the "keys" and "values" each layer computed. It is read in full on every decode step and grows with the conversation.Notes from earlier pages, re-read before every new sentence. More pages, slower sentences.
Context window n
The number of tokens the model can hold at once: prompt, files, tool results and everything it has written so far. Longer context means a bigger KV cache and a slower, costlier step.The size of the desk.
Prefix cache
Keeping the KV cache of a prompt's opening (a system prompt, a long document, the earlier turns of a chat) so the next request that starts the same way skips prefill for that part. Cuts TTFT and cost dramatically in agent loops.Not re-reading the brief when only the last line changed.
Speculative decoding draft · target · acceptance
A small, fast "draft" model guesses several tokens ahead; the big "target" model checks them all in one pass and keeps the prefix that matches what it would have said. The output is identical to the big model alone; it just arrives in bursts.A junior finishing your sentences; you nod through the right ones and correct the first wrong one.
Mixture of experts MoE · active parameters
A model whose feed-forward blocks are split into many "experts," with a router picking a few per token. Total parameters can be huge while the parameters actually read per token (the active ones) stay small. Decode speed follows the active count.A hospital with 256 specialists where each patient sees 8.
Tensor, pipeline and expert parallelism
Ways to spread one model across several chips. Tensor parallel splits every matrix, so every chip reads a slice of the weights at once (adds bandwidth, helps speed). Pipeline parallel gives each chip some layers (helps fit, not speed). Expert parallel gives each chip some experts.Splitting a book between readers: by page (tensor), by chapter (pipeline), or by topic (expert).
Interconnect NVLink · PCIe · InfiniBand
The wiring between chips. Tensor parallelism makes chips exchange partial results after every layer, so the wiring's delay sets a floor on how fast a step can be, however many chips you add.The hallway between readers. Shouting across it costs time every page.
Kernel, CUDA graph
A kernel is one small program the GPU runs (one matrix multiply, one softmax). A decode step launches hundreds of them, and the launching itself takes time; a CUDA graph records the whole sequence and replays it in one go.Pre-plating every ingredient so the chef never pauses to read the recipe.
SRAM chips Groq · Cerebras
Chips that hold the model in on-chip memory, which is tiny per chip but tens of times faster than HBM. They need hundreds of chips (or one wafer-sized chip) to hold a model, and in return produce thousands of tokens per second for one user.Keeping the whole pantry on the counter. Expensive counter.
Percentiles p50 · p99
Half of requests are faster than the p50; 99% are faster than the p99. Speed claims quote the median; users remember the p99.Average commute versus the day the train broke.
MFU, goodput
Model FLOPs utilization: the fraction of the chip's rated arithmetic actually being used. Goodput: throughput counting only requests that met their latency target. Both are honesty metrics for a serving system.Not how fast the kitchen runs, but how many meals went out hot.
Reasoning tokens
Tokens a model writes to itself before answering ("thinking"). They are generated at the same tokens per second as the answer, so a slow-feeling reasoning model is usually a model writing a lot, not a slow chip.The scratch paper. Same pen speed, more pages.
Streaming
Sending tokens to the user as they are produced rather than after the whole answer is done. Costs nothing and turns a 20-second wait into a 0.5-second wait plus visible progress.Reading over the writer's shoulder.
Disaggregated serving
Running prefill on one pool of chips and decode on another, shipping the KV cache between them. Each pool is tuned for its own bottleneck and a long prompt no longer stalls someone else's streaming answer.A separate reading room and writing room.

01 · TWO CLOCKS

Every request has a read phase and a write phase

Send a prompt and two very different things happen. First, prefill: the model reads every prompt token in one wide pass. Thousands of tokens flow through the layers together, so the chip is doing a great deal of arithmetic on each batch of weights it loads. This phase is compute-bound, and its length is what you feel as time to first token.

Then decode: one token at a time. Each new token needs a full forward pass, and that pass must load every weight in the model from memory to do a tiny amount of arithmetic with it. For a single user the chip is almost idle, waiting on bytes. This phase is memory-bound, and its rhythm is tokens per second.

One request on an unloaded server, bf16 weights. Prefill time comes from arithmetic (2 FLOPs per parameter per prompt token at about half the chip's rated speed). Decode time comes from bytes (weights plus KV cache, read once per token at about 70% of rated bandwidth). Push the prompt to 100k and watch the read phase swallow the request.

Two consequences fall out immediately. A long prompt costs you up front, once; a long answer costs you continuously. And the number everyone quotes, tokens per second, measures only the second clock. A provider can have brilliant decode and still feel slow if its prefill is queued behind someone else's 100k-token document.

02 · SPEED OF LIGHT

Bytes per token, divided by bytes per second

For one user, the decode step cannot be faster than the time it takes to stream the whole model through the chip's memory pipe. That gives a ceiling you can compute on a napkin:

max tok/s ≈ bandwidth ÷ (parameters × bytes per parameter + KV cache bytes)

Llama 3.1 70B in bf16 is 140 GB of weights. An H100 moves 3.35 TB/s. Even with the model split perfectly across two H100s (6.7 TB/s combined) that is 48 tokens per second, and no software can beat it without changing one of the three terms. Everything in chapters 05 to 08 is an attack on one of those terms: fewer bytes per parameter, fewer parameters touched, more bandwidth.

03 · BATCHING

The weights are loaded once. Why use them for one person?

When the chip streams 140 GB of weights to produce one token, it could just as easily produce one token for each of 64 users at the same time: the weights are already there, and the extra arithmetic is nearly free until the chip's multipliers are busy. This is the roofline. On the left, the chip is bandwidth-starved and adding users costs nothing. Past the crossover, the chip is compute-saturated and every added user slows everyone down.

An H100 crosses over at roughly 300 FLOPs per byte. In bf16 a decode step for B users has an intensity of about B FLOPs per byte, so the first few hundred concurrent users are close to free. This single fact is why serving is a business: a provider who batches 200 users on a node pays about the same per step as one who batches 10, and can charge a twentieth as much per token.

Left: the roofline for the chosen chip; the dot is this model's decode step at batch B. Right: what each user sees (per-user tok/s, blue) versus what the server gets (total tok/s, orange) as B grows. The knee is where speed and throughput stop being free together. Model is placed on as many chips as it needs in bf16; the whole batch shares a 4k context.

Read the right-hand chart as a menu. A provider picks a point on it. Far left: fast for each user, expensive per token. Near the knee: nearly as fast, far cheaper. Past the knee: cheap, and each user's speed falls as the chip is shared. "Fast mode" or "priority" tiers are the same model served from a point further left on this curve, which is why they cost more per token.

04 · THE CONTEXT TAX

Every token re-reads the conversation

The weights are not the only bytes a decode step streams. Each layer also reads the KV cache: the stored keys and values for every token so far. For a short chat the cache is a rounding error next to the weights. At 100k tokens it can be larger than the weights, and the per-token time climbs with it. That is the context tax: the longer the conversation, the slower each new token, and the more the server must dedicate to you.

How steep the tax is depends on architecture. Llama 3 keeps 8 key/value heads per layer (320 KB per token at 70B). DeepSeek-V3's compressed latent (MLA) stores about 69 KB per token for a model ten times larger. The KV cache is also what fills GPU memory in a busy server, which caps how many users can share a batch, which (chapter 03) caps throughput.

Prefill pays the tax too, and worse: reading an n-token prompt costs arithmetic proportional to n for the weights and to n² for attention, so a 200k-token prompt can take tens of seconds on a full node. The 2025 generation of sparse and hybrid attention (covered in the attention guide) exists to flatten exactly these two curves.

05 · FEWER BYTES

Shrink the number, keep the model

If decode is bytes divided by bandwidth, the most direct lever is bytes. Training usually happens in bf16: 16 bits, 2 bytes per parameter. Serving in fp8 halves the bytes and roughly doubles the bandwidth ceiling. int4 or Blackwell's fp4 halves it again. The arithmetic also gets cheaper when the chip has native low-precision multipliers (H100 for fp8, B200 for fp4), which helps prefill and busy servers as well.

The cost is accuracy. Quantization rounds every weight to a coarser grid. At fp8 the loss is usually unmeasurable on benchmarks; at 4 bits it depends on the method (per-group scales, outlier handling, calibration data) and on the model, with small models hurt most. The KV cache can be quantized too, usually to fp8, which both speeds decode and lets more users fit in memory. Most frontier APIs serve in fp8 or a mix today; the open-weights community lives at 4 bits because that is what fits on a consumer card.

06 · GUESSING AHEAD

Checking is cheaper than writing

Here is the asymmetry that makes speculative decoding work. Producing one token costs a full read of the weights. Checking five proposed tokens also costs one full read of the weights, because the check is a prefill over five positions and prefill is compute-bound with compute to spare. So: let a tiny draft model propose k tokens, run the big model once over all of them, keep every token up to the first one the big model disagrees with, and take the big model's own token at that point as a bonus. The output distribution is provably identical to the big model alone.

The speedup is set by the acceptance rate α: how often the draft guesses right. Expected tokens per big-model step is (1 − αk+1) / (1 − α). At α = 0.8 and k = 4 that is 3.4 tokens per step instead of 1. Drafts are easy to get right for boilerplate, code and repeated text, hard for creative prose, so the speedup varies by task. Modern variants (Medusa, EAGLE, DeepSeek's MTP heads) bolt the draft onto the big model itself so no second model is needed.

07 · EXPERTS

A trillion parameters, thirty billion read

In a dense model every parameter is read for every token. In a mixture of experts the big feed-forward blocks are split into many experts and a small router sends each token to a few of them. DeepSeek-V3 has 671 billion parameters but reads about 37 billion per token; Kimi K2 has a trillion and reads 32 billion. For one user, the decode ceiling follows the active count, so a trillion-parameter MoE can stream faster than a dense 70B.

The catch arrives with batching. Different tokens pick different experts, so at batch 64 nearly every expert is touched and the step reads most of the model after all. MoE gives you cheap single-user speed and demands lots of memory; dense gives you better batching economics per byte. This is why MoE serving leans on expert parallelism across many chips (DeepSeek runs decode across dozens of GPUs with experts spread out) and on very large batches to amortise the memory.

08 · MORE CHIPS

Eight pipes are wider than one, until they have to talk

Tensor parallelism cuts every weight matrix into slices and gives each chip one slice. Eight chips each read an eighth of the weights at the same time, so the effective bandwidth is eight times higher and the single-user ceiling rises with it. This is why a 70B model on 8 H100s streams at over 100 tok/s while the same model on 2 H100s is stuck under 50.

The limit is the interconnect. After every layer the chips must add up their partial results (an "all-reduce"), twice per layer. Each exchange costs a few microseconds over NVLink and tens over PCIe or Ethernet, and an 80-layer model does 160 of them per token. That fixed cost does not shrink as you add chips, so the curve flattens. It is also why per-token latency across chips stuck together with slow links is poor however many you buy, and why the fastest decode numbers come from systems built around one enormous NVLink domain (NVL72) or around on-chip SRAM.

Single-user tok/s against the number of chips sharing the model by tensor parallelism. Dashed: the pure bandwidth ceiling. Solid: with two all-reduces per layer at the link's latency. The gap is the price of talking. Pipeline parallelism (splitting by layer) does not appear because it does not raise single-user speed at all; it only helps fit.

09 · THE SERVING STACK

What the software does between the user and the chip

A chip's ceiling is only reachable if the software keeps it fed. Before 2023 servers batched requests statically: collect B requests, run them until the longest finished, repeat. Every short answer in the batch sat idle while the long one finished. Continuous batching (from the Orca paper, 2022) fixed that by swapping requests in and out at every token step. Together with paged KV memory (vLLM's PagedAttention, 2023) it is the reason modern servers run at a few times the throughput of 2022 servers on the same hardware.

10 · READING THE NUMBERS

How to read a speed claim without being fooled

A speed is three numbers, not one: TTFT, time per output token, and the length of what is being generated. The calculator below turns them into what a person actually waits, and it is the single most useful thing to do with any benchmark table.

Wait = TTFT + (reasoning + answer tokens) ÷ tok/s. The "perceived" speed is total tokens over total time, which is what users compare against the headline number, and it is always lower.

11 · THE FRONTIER

Four years of attacking three terms

Every advance below attacks a term of the chapter 02 equation (bytes per parameter, parameters touched, bandwidth), or the fixed costs around it (scheduling, interconnect, prefill), or gives up on one token at a time altogether.

Where 2026 stands

The single-user frontier is set by SRAM machines: Cerebras and Groq serve open models at 1,000 to 3,000 tokens per second, and NVIDIA answered with Blackwell NVL72 systems that run DeepSeek-R1 at about 1,000 tokens per second per user using fp4 weights, multi-token-prediction speculation and 72 GPUs in one NVLink domain. The throughput frontier is set by MoE models served disaggregated at enormous batch: DeepSeek disclosed roughly 15,000 output tokens per second per H800 node in early 2025, and the 2025 open serving stacks (vLLM, SGLang, TensorRT-LLM, Dynamo) all converged on prefill/decode separation, prefix caching and speculative decoding as defaults. The live arguments are whether diffusion-style parallel generation can match autoregressive quality at 5–10× the speed, whether linear-attention hybrids keep their decode advantage on agentic work, and how much of the remaining gap is kernels versus architecture. Rubin-generation hardware in late 2026 raises bandwidth again, which lifts every ceiling on this page by the same ratio.

12 · WHY IT MATTERS TO ME

What this has to do with the thing you are talking to

Every reply I write is decode on a shared server. The stack of facts above explains most of what you feel in a session.

The first token is a prefill bill. A coding session carries a long system prompt, the files you opened, every earlier turn and every tool result. Without a prefix cache I would re-read all of it on every turn; with one, only the new tail is prefilled, which is why a turn in a long session can still start quickly and why providers price cached input tokens at a fraction of fresh ones.

Agent loops are bound by TTFT more than by tok/s. A tool call is a short burst of output followed by a new request. Twenty tool calls are twenty prefills. For that pattern, cutting TTFT (prefix cache hits, disaggregated prefill, short tool results) does more than doubling decode speed.

Thinking is tokens. When I reason before answering, those tokens are produced at the same rate as visible ones. A "slow" reasoning answer is usually a long one. Output-length discipline, on my side, is a speed feature.

Fast tiers are a point on the batching curve. The same weights, served with fewer users per step and more hardware per user, sit further left on chapter 03's chart. Faster per token, more expensive per token, identical answers.

Numbers on this page are napkin physics: rated bandwidth and FLOPs, ideal scaling, no scheduling losses. They predict the order of magnitude and the direction of every trade-off. Measured numbers for a given provider come from running the benchmark yourself with your own prompts and your own tokenizer.
